## PART 1 — FOUNDATIONS AND CLASSICAL CIPHERS

**1.** The key is independent so that security rests on the key alone, not on the algorithm remaining unknown. This is Kerckhoffs's principle. If the algorithm were the secret, then every disclosure — a leaked implementation, a reverse-engineered device, a departing employee — would compromise every user simultaneously and permanently, since algorithms cannot be changed cheaply. With an independent key, a compromise affects only the parties sharing that key, and recovery is as simple as generating a new one. It also allows the algorithm to be published and subjected to public cryptanalysis, which is how confidence in a cipher is actually established.

**2.** Keyspace size only bounds the *brute force* effort; it says nothing about whether a cleverer attack exists. A monoalphabetic cipher preserves the statistical structure of the plaintext exactly — each plaintext letter maps consistently to one ciphertext letter, so English letter frequencies, digraph patterns and word shapes survive the encryption intact. The attacker never enumerates keys; they read the structure directly off the ciphertext. DES's 56-bit key is criticised on entirely different grounds: DES has no comparable structural weakness, so brute force *is* the best available attack, which makes the keyspace size the binding constraint. The lesson is that a large keyspace is necessary but nowhere near sufficient.

**3.** The Caesar cipher applies a single fixed shift to every letter, so the entire frequency distribution is merely rotated and remains fully readable. The Vigenère cipher is polyalphabetic: the repeating keyword means a given plaintext letter is encrypted under a different shift depending on its position, so E does not map to one ciphertext letter but to as many distinct letters as the key is long. This flattens the frequency distribution and destroys the one-to-one statistical correspondence frequency analysis depends on. (It is not unbreakable — once the key length is recovered, the ciphertext decomposes into several Caesar ciphers, each individually vulnerable.)

**4.** Reuse destroys the perfect secrecy that justifies the entire scheme. If C₁ = P₁ ⊕ K and C₂ = P₂ ⊕ K, then C₁ ⊕ C₂ = P₁ ⊕ P₂ — the key cancels completely and the attacker obtains the XOR of two plaintexts with no key knowledge whatsoever. Since natural-language plaintexts are highly redundant, this combined value can be separated into its two components by statistical techniques (crib dragging), recovering both messages. The security of the OTP rests on the key being an unrepeated random mask; used twice, it is no longer a mask at all but a shared, cancellable term.

**5.** Rail Fence is a transposition cipher: it reorders the positions of the plaintext letters without changing their identities. This matters directly for cryptanalysis because the letter frequency distribution of the ciphertext is *identical* to that of the plaintext — so frequency analysis, the standard first tool against substitution, tells the attacker nothing about which letters map to which. Instead the attack targets the permutation itself: anagramming, testing candidate depths or rail counts, and exploiting the fact that the plaintext letters are all present and merely rearranged. Classifying the cipher correctly is what tells you which attack to reach for.

## PART 2 — BLOCK CIPHERS, DES AND AES

**6.** The benefit is that decryption requires no inverse of the round function F. Because only half the block is altered per round and the alteration is applied via XOR, running the identical round structure with the subkeys in reverse order exactly undoes the encryption — F is never inverted and need not even be invertible. This is a substantial practical gain: F can be arbitrarily complex, nonlinear and one-way, chosen purely for cryptographic strength rather than for invertibility, and a single piece of hardware or code serves both encryption and decryption. Transforming the whole block per round would mix faster but would force every component to be invertible and would require a separate inverse cipher, which is precisely the trade-off AES later accepted.

**7.** Every other stage in the DES round function is **linear**. Expansion duplicates bits, permutation reorders them, and XOR with the subkey is linear over GF(2). A cipher built purely from linear operations, no matter how many rounds, collapses into a single equivalent linear transformation that can be solved directly by linear algebra. The S-boxes are the sole **nonlinear** component, and they are therefore the only thing preventing that collapse. The linear stages are not useless — they provide diffusion, spreading the S-boxes' nonlinear effect across the block — but the security itself originates in the S-boxes. This is also why the S-box design was scrutinised so heavily and why they were later shown to have been deliberately hardened against differential cryptanalysis.

**8.** They serve implementation, not cryptography. IP and IP⁻¹ are fixed, publicly known, key-independent permutations, so an attacker can strip them off trivially and they add nothing to security. They are believed to have been included to suit the bit-loading characteristics of 1970s hardware, easing the movement of data into and out of the chip. The exam-relevant point is the distinction itself: a transformation that does not depend on the key cannot contribute security, however thoroughly it scrambles the bits.

**9.** Without the avalanche effect, related plaintexts produce related ciphertexts, and that relationship is exploitable. An attacker can then make small controlled changes to the input, observe the correspondingly small changes in the output, and use the correlation to work backwards toward the key — this is the basis of **differential cryptanalysis**. A strong avalanche effect means a one-bit input change flips roughly half the output bits unpredictably, so no usable correlation between input differences and output differences survives. It is therefore a deliberate design target, not a happy accident.

**10.** Triple DES extends the key length but inherits DES's other parameters, chiefly the **64-bit block size**, which no amount of key lengthening can fix. A 64-bit block means collisions among ciphertext blocks become likely after roughly 2³² blocks by the birthday bound, leaking plaintext relationships in long sessions (the basis of the Sweet32 attack). It is also roughly three times slower than DES, having been built by repetition rather than redesign, which is poor value on modern hardware. Triple DES was a stopgap that preserved compatibility with deployed DES infrastructure while a genuinely new cipher with a larger block, larger key and modern design was standardised — AES.

**11.** AES gains speed and stronger per-round diffusion. Because the entire 128-bit State is transformed each round rather than half of it, AES achieves adequate mixing in 10 rounds where DES needs 16, and its byte-oriented operations map efficiently onto both software word operations and hardware. What it gives up is the Feistel structure's central convenience: since every transformation must now be individually invertible, decryption requires a genuinely separate inverse cipher (InvSubBytes, InvShiftRows, InvMixColumns) rather than simply reversing the subkey order. AES accepted a more complex implementation in exchange for a faster, cleaner and more analysable design.

**12.** MixColumns exists to diffuse influence within a column so that *subsequent* rounds spread it further. After the final AddRoundKey there are no subsequent rounds, so the diffusion it would provide is never compounded and confers no additional security. Omitting it is safe because nothing is weakened: the last round still applies substitution, permutation and the key. There is also a positive reason for the omission — it makes the encryption and decryption structures symmetric, avoiding a pointless InvMixColumns step in the inverse cipher. The final operation being AddRoundKey also ensures the ciphertext is masked by key material as its last act.

**13.** Reusing the same key in every round would make the rounds structurally identical and introduce exploitable symmetry, most seriously **slide attacks**, which work precisely when a cipher's rounds are indistinguishable from one another. It would also mean a single relationship between input and output holds across all rounds, greatly assisting related-key and differential analysis. Key expansion produces a distinct, nonlinearly derived subkey per round — using byte rotation, S-box substitution and round constants — so each round is different, the round constants break the symmetry between rounds, and the nonlinearity means recovering one round key does not immediately yield the others or the master key.

**14.** Because the other three transformations are fixed and public, they contribute **confusion and diffusion** but no secrecy — anyone can compute or invert SubBytes, ShiftRows and MixColumns without any key. Their role is to make the relationship between input and output complex; AddRoundKey's role is to make it *secret*. The design separates these two concerns deliberately: the public transformations provide the cryptographic mixing, and injecting key material between them ensures that an attacker who understands the mixing perfectly still cannot proceed without the key. The two elements are only secure in combination — key XOR alone would be trivially broken, and the public transformations alone would require no key at all.

## PART 3 — FINITE FIELDS

**15.** A field is required because it guarantees **division**, that is, every nonzero element has a multiplicative inverse. In a ring this is not assured, so some elements simply cannot be undone. Cryptography needs this in two concrete places on this syllabus. First, invertibility of transformations: AES's S-box is constructed from multiplicative inverses in GF(2⁸) and MixColumns must be reversible for decryption to work, which requires the underlying arithmetic to support inverses. Second, key generation: RSA's private exponent d is defined as the multiplicative inverse of e modulo φ(n), and if inverses were not guaranteed to exist for coprime elements, RSA key generation could not proceed at all.

**16.** A field requires every nonzero element to have a multiplicative inverse, and modulo a composite n, any element sharing a factor with n has none. Concretely, take n = 6 and the element 2: 2×1 = 2, 2×2 = 4, 2×3 = 6 ≡ 0, 2×4 = 8 ≡ 2, 2×5 = 10 ≡ 4. The product never equals 1, so 2 has no inverse mod 6 and {0,…,5} is not a field. Compare n = 7, which is prime: 3×5 = 15 ≡ 1, 2×4 = 8 ≡ 1, 6×6 = 36 ≡ 1, and so on — every nonzero element has an inverse. Primality guarantees that no element below the modulus shares a factor with it, and that is exactly what makes the inverses exist.

**17.** Degree alone only ensures the results have the right number of bits; it says nothing about the algebraic structure. An irreducible polynomial is the polynomial analogue of a prime: it cannot be factored into lower-degree polynomials, so no nonzero element can share a factor with the modulus. If a reducible polynomial such as x⁴ is used, elements sharing a factor with it lose their multiplicative inverses by exactly the mechanism that fails for composite moduli in GF(p), and the structure degrades from a field to a ring. Reduction modulo x⁴ also amounts to mere truncation of high-degree terms rather than genuine modular reduction. The requirement is the same one seen throughout: prime for integers, irreducible for polynomials, for identical reasons.

**18.** The integers modulo 256 do **not** form a field, because 256 is composite — every even number shares the factor 2 with the modulus and therefore has no multiplicative inverse. Since AES needs invertible transformations (the S-box is built from multiplicative inverses; MixColumns must be reversible for decryption), arithmetic mod 256 would leave half the byte values without inverses and the construction would fail. GF(2⁸) solves this: it has exactly 256 elements, so it still maps perfectly onto a byte, but because it is built as polynomials modulo an irreducible polynomial, every one of its 255 nonzero elements has a multiplicative inverse. AES gets byte-sized arithmetic *and* a genuine field, which mod-256 integer arithmetic cannot provide.

## PART 4 — MODES OF OPERATION AND STREAM CIPHERS

**19.** The fault lies in the **mode's determinism**, not in the cipher. ECB computes C_i = E(K, P_i) with no dependence on block position, on any previous block, or on any IV or nonce. Since E under a fixed key is a deterministic function, equal inputs must produce equal outputs: if P_i = P_j then necessarily C_i = C_j. Real plaintexts are highly repetitive — repeated headers, padding, uniform image regions, recurring database field values — so the repetition pattern of the plaintext is copied faithfully into the ciphertext. No key is recovered and the cipher is not broken; the information leaks through the *pattern of equalities* between blocks, which the mode does nothing to conceal. Every other mode fixes this by introducing something that varies block to block.

**20.** Chaining makes each block depend on its predecessor, but the *first* block has no predecessor. Without an IV, C₁ = E(K, P₁) — pure ECB for that block — so two messages beginning with the same block would produce identical first ciphertext blocks, and since chaining propagates forward, they would remain identical for as long as the messages agreed. Encrypting the same message twice would then yield byte-identical ciphertext, revealing repetition across sessions. The IV seeds the chain with a fresh, unpredictable value so that even identical plaintexts encrypt differently every time, making the encryption **probabilistic** rather than deterministic.

**21.** They defend against different things. CBC computes C₁ = E(K, P₁ ⊕ IV), so the IV is XORed directly with attacker-influenced plaintext; a predictable IV allows an attacker who can choose plaintext to cancel it out and mount a chosen-plaintext distinguishing attack (the basis of the BEAST attack on TLS). Unpredictability is therefore required, not merely freshness. In CTR the counter is not combined with plaintext at all — it is an input to E, which produces a keystream. Nothing is gained by an attacker knowing the counter value, since they cannot compute E without the key. What is fatal is *repetition*: two blocks encrypted under the same (key, counter) share a keystream, and XORing their ciphertexts cancels it, exposing the XOR of the plaintexts exactly as in one-time pad reuse. Hence unpredictability for CBC, uniqueness for CTR.

**22.** E is applied to the **IV or the previous ciphertext block**, never to the plaintext. CFB computes C_i = P_i ⊕ E(K, C_(i−1)): the block cipher's only job is to manufacture a keystream from a value that both parties already possess, and the plaintext is combined with that keystream by XOR alone. The receiver holds C_(i−1) too, so it regenerates the identical keystream with the same forward operation E, and since XOR is self-inverse, C_i ⊕ E(K, C_(i−1)) returns P_i. D is never needed because nothing was ever put through E in the forward direction that needs taking back out. A useful consequence: the underlying block cipher's decryption function need not even be implemented for CFB, OFB or CTR.

**23.** The difference is what each keystream block is derived from. OFB generates its keystream by iterated encryption of the previous keystream block, O_i = E(K, O_(i−1)), so block i's keystream is unobtainable until blocks 1 through i−1 have been computed in sequence — an inherently serial dependency chain that no amount of hardware can shortcut. CTR derives block i's keystream as E(K, Counter_i), and every counter value is known in advance and independently of every other. Any block, or all blocks at once, can therefore be computed immediately and in any order. Both modes share the property that the keystream is independent of the *ciphertext*, which is why neither propagates errors; they differ in whether the keystream depends on *itself*, which is what governs parallelism.

**24.** It matters wherever data is large and accessed non-sequentially — full-disk and database encryption being the standard cases. Reading sector 40,000 of an encrypted disk should cost one block decryption, not 40,000; without random access the entire scheme becomes unusable at scale. CBC cannot offer it for encryption because C_i = E(K, P_i ⊕ C_(i−1)) requires the previous ciphertext block, forming a strict serial chain. (CBC *decryption* is in fact parallelisable, since all the needed ciphertext blocks are already in hand, but the encryption dependency and the chain semantics still make it a poor fit for random-access storage compared with CTR, where any block's keystream derives from its counter alone.)

**25.** Statistical randomness and cryptographic unpredictability are distinct requirements, and standard test suites only check the former. An LCG produces well-distributed, uncorrelated-looking output, which is entirely adequate for a simulation, where the adversary is sampling error rather than an intelligent attacker. Cryptography additionally demands that an adversary who has observed part of the output cannot predict the remainder. The LCG fails absolutely: its next-state relation X_(n+1) = (aX_n + c) mod m is a simple linear equation, so a handful of consecutive outputs suffices to solve for a, c and m, after which the entire past and future keystream is reproducible. In a stream cipher the ciphertext is plaintext XORed with the keystream, so recovering the keystream recovers every message. The property genuinely required is that of a CSPRNG.

**26.** Because in a stream cipher the keystream *is* effectively a one-time pad, and reusing it makes the key cancel. If C₁ = P₁ ⊕ KS and C₂ = P₂ ⊕ KS, then C₁ ⊕ C₂ = P₁ ⊕ P₂: the attacker obtains the XOR of two plaintexts with no knowledge of the key at all, and the redundancy of natural language then separates them. A block cipher key, by contrast, is not combined with plaintext by XOR; it parameterises a complex keyed permutation, and reusing it across messages is normal and expected practice — indeed unavoidable. What must not be reused with a block cipher is the *IV or counter*, and the reason is precisely that doing so recreates the stream-cipher failure by producing a repeated keystream. The distinguishing factor is whether the reused quantity is a mask that cancels under XOR.

## PART 5 — NUMBER THEORY AND PUBLIC-KEY CRYPTOGRAPHY

**27.** Because the RSA modulus n = pq is **composite**, and Fermat's Little Theorem applies only to a prime modulus. The correctness argument requires a statement of the form a^(something) ≡ 1 for the modulus actually in use, and for composite n that statement is Euler's Theorem: a^φ(n) ≡ 1 (mod n) whenever gcd(a, n) = 1. This is exactly why d is defined as the inverse of e modulo φ(n) rather than modulo anything else — so that ed = 1 + kφ(n) and hence P^(ed) = P·(P^φ(n))^k ≡ P (mod n). Fermat's Little Theorem is the special case n prime, where φ(p) = p − 1; it underpins the primality testing used to *find* p and q, but it cannot carry the correctness proof for the composite modulus itself.

**28.** Because knowledge of p and q yields φ(n) = (p−1)(q−1) immediately, and φ(n) yields the private key: d is simply the inverse of the public e modulo φ(n), computable in moments by the extended Euclidean algorithm. Publishing n is safe only because recovering p and q *from* n requires integer factorisation, which is infeasible for suitably large primes — that difficulty is the whole of RSA's security. The asymmetry is the entire point: the legitimate key holder built n from p and q and so knows φ(n) for free, while an attacker holding only n faces the factorisation problem. Retaining p and q after key generation therefore serves no purpose beyond enabling CRT-based decryption speedups, and any leak of them is total compromise.

**29.** Because d is defined as the multiplicative inverse of e modulo φ(n), and **that inverse exists only when gcd(e, φ(n)) = 1**. If e shares a factor with φ(n), the congruence ed ≡ 1 (mod φ(n)) has no solution whatsoever, so step 5 of key generation simply cannot be completed — there is no valid private exponent to find. The condition is not a security heuristic but an existence requirement inherited directly from modular arithmetic: an element is invertible modulo m precisely when it is coprime to m. This is the same rule that governs GF(p) and GF(2ⁿ), surfacing again in a different setting.

**30.** The two moduli play different roles at different stages. φ(n) governs the *exponents*: it is the modulus in which e and d are inverses, because Euler's Theorem makes exponents behave cyclically with period φ(n). n governs the *values*: plaintexts and ciphertexts are elements of Z_n, and Euler's Theorem is a statement about congruences modulo n. Reducing the message modulo φ(n) would be meaningless — φ(n) is not the space the message lives in, and worse, φ(n) is secret, so a receiver holding only the public key could not perform the operation at all. The relationship is best stated as: work modulo n on the base, modulo φ(n) on the exponent. Conflating them is the single most common RSA error.

**31.** Because RSA requires primes of hundreds of digits, and trial division would require testing divisors up to the square root of a number with several hundred digits — computationally impossible, not merely slow. Miller-Rabin runs in polynomial time and returns either "definitely composite" or "probably prime". The uncertainty is acceptable because it is **one-sided and quantifiable**: a composite is never wrongly certified after a failed test, and each additional random witness reduces the probability of a composite passing by a factor of at least four. After enough independent rounds the error probability falls below the probability of an undetected hardware fault or cosmic-ray bit flip during the computation, at which point insisting on certainty is not engineering but superstition.

**32.** It is used because RSA decryption computes C^d mod n with a full-size exponent and modulus, which is expensive. CRT allows the holder of p and q to compute the result modulo p and modulo q separately — each with numbers roughly half the bit length, and hence far cheaper, since modular exponentiation cost grows faster than linearly — then recombine the two results uniquely modulo n = pq. The speedup is typically around fourfold. It does not weaken security because it requires knowledge of p and q, which only the private key holder possesses; it is an optimisation available exclusively to the legitimate party and gives an attacker nothing. (The practical caveat, worth a mark if mentioned, is that a fault during CRT decryption can leak a factor of n, so implementations verify the result before releasing it.)

**33.** The mechanism is the **commutativity of exponentiation**: (α^(X_A))^(X_B) and (α^(X_B))^(X_A) both equal α^(X_A·X_B), so the two parties reach the same value by applying their own secret exponent to the other's public value. What travels across the channel is α^(X_A) mod q and α^(X_B) mod q; the secret exponents X_A and X_B never leave their owners, and the shared key α^(X_A·X_B) is never transmitted in any form. An eavesdropper holding α, q, α^(X_A) and α^(X_B) would need to combine the last two into α^(X_A·X_B), and no known method does this without first solving for one of the exponents — the discrete logarithm problem. The secret is *computed independently at both ends* rather than sent, which is precisely why interception of the transmitted values is not enough.

**34.** Because the attack does not attempt the mathematics at all — it attacks the **binding between a public value and an identity**, which the protocol never establishes. The attacker substitutes their own public value in each direction, performing one perfectly ordinary and mathematically sound Diffie-Hellman exchange with Alice and another with Bob. Two legitimate shared keys result; the attacker simply holds both, decrypting and re-encrypting traffic in transit. No discrete logarithm is ever computed and no cryptographic assumption is violated. This illustrates a general principle: the strength of a primitive bounds only the attacks that engage with the primitive, and an unauthenticated protocol can be defeated entirely around the mathematics. The remedy is to authenticate the exchange, through signatures or certificates.

**35.** Chiefly because public-key operations are **orders of magnitude slower** than symmetric ones — RSA and ECC rest on modular exponentiation or point multiplication over very large operands, while AES is built from byte substitutions, shifts and XORs and is hardware-accelerated on most modern processors. Encrypting bulk data asymmetrically would be prohibitively expensive. Secondary reasons: RSA can only encrypt messages smaller than the modulus, requiring padding schemes and block handling; and raw RSA is deterministic, so it needs randomised padding to avoid the same leakage that afflicts ECB. Practice therefore uses **hybrid encryption** — public-key cryptography solves key distribution by transporting or agreeing a symmetric key, and a symmetric cipher then does the bulk work. Each is used for what it is good at.

**36.** Because the two problems have different **attack complexities**, not merely different appearances. Integer factorisation admits sub-exponential algorithms, chiefly the general number field sieve, which run far faster than brute force and force RSA moduli to grow rapidly to stay ahead — hence 3072 bits for a modern security margin. The elliptic curve discrete logarithm problem admits no known sub-exponential attack on well-chosen curves; the best general methods, such as Pollard's rho, are fully exponential at roughly the square root of the group order. A 256-bit ECC key therefore delivers about 128 bits of security, matching 3072-bit RSA. The gain is not that elliptic curves are somehow "more secure" in kind, but that the best known attacks against them scale far worse for the attacker, so far fewer key bits are needed per bit of security.

## PART 6 — SYNTHESIS

**37.** Because security is a property of the whole system, and the algorithm is only one component; several distinct failure modes have appeared in this course, none of which involve breaking a cipher.
- **Mode of operation**: AES in ECB leaks plaintext structure through repeated blocks despite AES itself being unbroken. The fault is the mode's determinism, not the cipher.
- **Parameter reuse**: reusing an IV in CBC or a counter in CTR, or a keystream in a stream cipher, leaks the XOR of plaintexts while the underlying cipher performs exactly as specified.
- **Protocol-level omission**: Diffie-Hellman falls to a man-in-the-middle attack with the discrete logarithm problem entirely intact, because the protocol never authenticates identities.
- **Key generation and management**: RSA collapses the moment p, q or φ(n) leaks, regardless of the modulus size.
A defensible claim of security must therefore address the algorithm, the mode, the parameters, the protocol and the key lifecycle. Any of them alone is sufficient to lose everything.

**38.** Because XOR is its **own inverse** (A ⊕ A = 0, hence (P ⊕ K) ⊕ K = P), which makes a single operation serve in both directions and lets a single piece of code or hardware encrypt and decrypt. It is also perfectly balanced: XOR with a uniformly random bit produces a uniformly random output regardless of the input bit, so it leaks nothing about the plaintext when the mask is random — the property that gives the one-time pad its perfect secrecy and that every keystream-based mode inherits. It is bitwise, so it needs no carry propagation and is essentially free in hardware and a single instruction in software. And it is linear over GF(2), which is what allows the Feistel construction to guarantee reversibility even when F is arbitrarily complex and non-invertible. Reversibility, balance, speed and linearity in one operation is a rare combination; no common alternative offers all four.

**39.** Both need an operation that is cheap to perform and infeasible to reverse, so that the public key can be derived from the private key while the reverse derivation is out of reach: RSA uses multiplication of large primes (easy forward, factorisation hard backward), Diffie-Hellman uses modular exponentiation (easy forward, discrete logarithm hard backward). Without this asymmetry there is no separation between public and private and the whole concept fails. But "hard" here means **computationally infeasible with known algorithms and available resources**, not impossible in principle — the answers exist and are perfectly well defined, and brute force always terminates eventually. Three consequences follow. Security is a moving target: better algorithms or faster hardware erode it, which is why key sizes have grown over time. Security is quantitative: it is stated as a work factor, not as a guarantee. And it is contingent on assumptions: no proof exists that factorisation is genuinely hard, and a mathematical advance — or a sufficiently large quantum computer running Shor's algorithm — would break both problems outright.

**40.** Because the two choices sit at different points on the curve of diminishing returns. AES-128 already provides a work factor of 2¹²⁸, which is beyond any foreseeable brute-force capability; moving to AES-256 raises a number that was already unreachable and closes no practical attack path. Mode selection, by contrast, decides whether the system has an exploitable weakness at all: ECB leaks plaintext structure regardless of key size, a predictable CBC IV enables chosen-plaintext attacks, and a repeated CTR counter exposes the XOR of plaintexts. These are practical, demonstrated attacks that succeed against AES-256 exactly as readily as against AES-128, because they never engage the key. The general lesson is that attackers pursue the cheapest available route, and mode and parameter errors are almost always cheaper than attacking the cipher — so effort spent on correct mode selection and parameter handling buys far more real security than effort spent enlarging an already sufficient key.
